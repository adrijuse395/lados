## Firefox (AMO) 0.4.0 — release notes & notes to reviewer

**Release notes** (shown to users):

```
Lados now pairs with this extension instead of trusting anything on the computer. Copy the code
from Lados ▸ Settings ▸ Browser pairing and paste it into the Lados popup once. From then on, Lados
asks you to allow each password it fills.
```

**Notes to reviewer:**

```
Pairing and user consent — the extension now talks to the desktop app differently.

Changed:
- background.js sends a pairing code with every request to the local bridge
  (http://127.0.0.1:18765). The code is generated by the Lados desktop app and pasted once by the
  user into the extension popup; it is kept in storage.local and never leaves the machine.
- popup.html / popup.js gained that pairing field and a "Not paired" state.
- manifest: added the "storage" permission, used only to keep that code.

Why: previously anything on the machine could read the local bridge. The code narrows it to this
extension, and the desktop app now asks the user to allow each password hand-over.

Unchanged, for reference:
- add-on id: lados@adrijuse395.github.io (so this updates the same add-on)
- host permission: only http://127.0.0.1:18765/* — the local loopback bridge to the Lados desktop app
- content script on http(s)://*/* only to detect login forms on the page the user is on
- no remote code; nothing is contacted except the user's own machine
- data collection: none — the pairing code is a local secret, not user data

Source: https://github.com/ladospwm/lados/tree/main/browser-extension
Privacy policy: https://ladospwm.vercel.app/privacy
(source of truth: https://github.com/ladospwm/lados/blob/main/docs/PRIVACY.md)
```

## Firefox (AMO) 0.4.2 — release notes & notes to reviewer

**Release notes** (shown to users):

```
Filling is more careful: a hidden password field — off-screen, transparent, clipped, covered or
1x1 — is no longer filled. A field that is simply below the fold is still filled once you scroll
to it.
```

**Notes to reviewer:**

```
One behaviour change, in content.js only, in `isVisible`. It now also rejects a field that a page
hides behind: a parent with opacity:0, a 1x1 clip (sr-only), a zero-height overflow:hidden parent,
fully transparent text, or another element covering the field (checked with elementFromPoint at the
field centre). It no longer rejects a field just for being outside the viewport — a login form below
the fold is filled once scrolled to, and the field is re-checked when it is actually filled. This is
the honeypot pattern: the field the page controls receives the password while the visible one stays
empty. No manifest, permission or network change.

## Firefox (AMO) 0.4.1 — release notes & notes to reviewer

**Release notes** (shown to users):

```
Filling is more careful: a login field a page hides or moves off-screen is no longer filled.
```

**Notes to reviewer:**

```
One behaviour change, in content.js only. `isVisible` now also checks each field's bounding box
against the viewport, plus its opacity and size, so a password field that a page has moved
off-screen (the classic `position:absolute; left:-9999px` trap) or made invisible is skipped instead
of filled. That is the honeypot pattern: the field the page controls received the password while the
visible one stayed empty. No manifest, permission or network change.
```

## Chrome Web Store → “Privacy practices”

**Single purpose**
```
Fill username and password fields on web pages from the user's own local Lados vault.
```

**Justification — host permission `http://127.0.0.1:18765/*`**
```
Communicate only with the Lados desktop application running on the same computer. This is
the local loopback bridge; no external server is ever contacted.
```

**Justification — `storage` permission**
```
Stores the pairing code the user copies from the Lados desktop app, so it survives a browser
restart. It is a local secret, not user data, and it is sent only to the Lados app on this
computer.
```

**Justification — content script on all sites (`http://*/*`, `https://*/*`)**
```
Detect login forms on the page the user is viewing so they can be filled on request from
their local vault. The extension reads only the page URL and the login fields; it does not
read or transmit page content.
```

**Remote code** — `No, I am not using remote code`
```
All code is bundled in the package. Nothing is downloaded or evaluated at runtime.
```

**Data usage** — declare **no data collected**:
```
This extension collects no user data. Nothing is transmitted off the device; there are no
analytics and no cookies. It keeps one local secret — the pairing code you copy from the Lados
app — in extension storage, and sends it only to the Lados app on this computer.
Check none of the "What user data do you plan to collect?" boxes.
```

**Privacy policy URL** — see `docs/PRIVACY.md` (must be a public URL; see below).

### Permission summary (for reference)

| Requested | Why |
| --- | --- |
| `host_permissions: http://127.0.0.1:18765/*` | Talk to the local Lados app only |
| `permissions: ["storage"]` | Keep the pairing code the user copies from the Lados app |
| Content script `http(s)://*/*` | Find login forms on the page you are on |

prefers 1280×800 but **downscales every screenshot to 640×400**, so avoid fine text.

### Screenshots

These are the **gallery images on the store page** — what a new user sees before installing.
They should show the extension *working*, must be a real capture (not a mock) of the latest
version, and be full bleed. To capture one:

1. `chrome://extensions` → **Developer mode** → **Load unpacked** → pick `browser-extension/build/chrome`.
2. Open a site with a login form while the Lados app runs and the vault is unlocked.
3. Screenshot the **“Fill with Lados”** pill; a second shot of the multi‑login picker is nice.

(For reference: the pill sits next to a login field; the picker lists several matching logins.)

The Markdown source of truth is `docs/PRIVACY.md`; the site page mirrors it. Fallback link if
reviewers need one: `https://github.com/ladospwm/lados/blob/main/docs/PRIVACY.md`.
